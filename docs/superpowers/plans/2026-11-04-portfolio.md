# Portfolio Landing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans for inline execution or superpowers:subagent-driven-development if selected by the user. Track steps below.

**Goal:** Реализовать утверждённый лендинг цифрового мастера для экспертов и бизнеса.
**Architecture:** Статические HTML/CSS и небольшие ES-модули; отдельный Node.js сервер обслуживает страницы и принимает обращения. Контент отделён от интерактивной логики. До настройки доставки форма сообщает о недоступности отправки и предлагает подтверждённые прямые контакты.
**Tech Stack:** HTML, CSS, browser JavaScript, Node.js LTS; node:test для серверной логики, браузерная проверка для интерфейса. Конкретную установленную версию проверить перед реализацией. Без CMS и клиентского фреймворка: для семи секций и локального демо они не требуются.
**Spec:** docs/superpowers/specs/2026-11-04-portfolio-design.md

## Global Constraints

- Семь секций в порядке ТЗ; русские тексты из раздела 4.
- Основной фон #F5F3EE, текст #17191D, акцент #3155E7; Manrope и IBM Plex Mono с проверкой лицензий.
- Диапазон от 320 px; проверки 320/375/768/1024/1440 px.
- Контакт 3–200 символов, задача 10–3000; серверная валидация.
- Никаких фиктивных отзывов, метрик, проектов и успешной отправки.
- Демо локальное и явно обозначено симуляцией.
- Начальный JS до 150 КБ gzip, главный визуал до 250 КБ, начальная передача до 1 МБ.
- Ключи только на сервере, обращения не отправляются в аналитику.
- Публикация требует реальных контактов, материалов, домена и схемы обработки данных.

## Review Focus

1. Отсутствующая интеграция доставки: форма не сообщает об успехе — задача 3.
2. Тайм-аут доставки и двойное нажатие: сохранён текст, повтор не создаётся автоматически — задача 3.
3. Контакт в мессенджере: не отвергается из-за отсутствия email — задача 3.
4. Отключённый JS и reduced motion: основной контент читается, движения отключены — задача 2.
5. Длинные русские тексты и увеличение масштаба: нет потери содержимого и горизонтального скролла — задача 4.

## Карта файлов

- public/index.html — семь секций, семантика, тексты и форма.
- public/styles.css — токены, сетка, состояния и адаптивность.
- public/app.js — меню, выбор направления, локальное демо и отправка формы.
- public/cases/*.html — подробные страницы только существующих проектов.
- public/assets/ — реальные изображения, локальные шрифты и лицензии.
- public/data-policy.html — фактические сведения после получения данных владельца.
- server.mjs — статическая раздача и маршрут POST /api/contact.
- lib/contact.mjs — валидация и отправка в согласованный канал.
- tests/contact.test.mjs — значимые проверки формы/доставки.
- package.json, .env.example — команды и имена конфигурации без секретов.
- README.md — запуск, контент, конфигурация и публикация.
- docs/verification.md — результаты проверок и ограничения запуска.

### Task 1: Статическая страница и визуальная система

**Interfaces:** сервер отдаёт public; index.html использует стабильные id intro/projects/services/process/about/faq/contact. Форма содержит contact, task, direction, website (honeypot).

- [ ] Проверить Node/npm, git и доступные инструменты браузера; изучить Sites skill для репозиторного сайта перед реализацией.
- [ ] Создать package.json с командами start (node server.mjs) и test (node --test); сервер статической раздачи ограничить public без обхода каталога.
- [ ] Создать index.html и styles.css: все тексты и секции из ТЗ, меню, footer, карточки и FAQ. Не публиковать выдуманные кейсы: использовать явно подписанные демонстрационные сценарии без клиентских заявлений.
- [ ] Подключить лицензированные локальные шрифты; если загрузка недоступна, временно использовать системные и записать ограничение. Отсутствующие портрет и реальные работы не заменять фиктивной личностью.
- [ ] Проверить HTTP 200 главной, наличие всех семи якорей и читаемость страницы без JS. Зафиксировать состояние в git только для файлов задачи.

### Task 2: Интерактивность и доступность

**Interfaces:** app.js читает data-direction у кнопок услуг, меняет поле direction, использует статические подготовленные вход/выход демо. FAQ на details/summary.

- [ ] Реализовать меню: aria-expanded, Escape, возврат фокуса, закрытие по якорю; не запирать доступ к основному содержимому.
- [ ] Реализовать выбор услуги и переход к форме без очистки введённого текста.
- [ ] Реализовать «Разобрать пример» и «Сбросить»; не обращаться к ИИ-сервисам, результат объявлять через live region.
- [ ] Добавить эффекты 150–220 мс и появление до 350 мс; reduced motion отключает движения. Основной контент виден при отказе скрипта.
- [ ] В браузере проверить клавиатуру, Escape, изменение направления, сброс демо, reduced motion и отсутствие JS. Результаты внести в docs/verification.md.

### Task 3: Форма и серверная доставка

**Interfaces:** validateContact(input) -> {ok, errors}; createContactHandler({deliver, limiter}) -> async handler; deliver({contact, task, direction}) -> Promise<void>. POST /api/contact принимает JSON; 200 только после подтверждения доставки, 400 валидация, 429 лимит, 503 отсутствие конфигурации/сбой. Ответ содержит только ok и понятный код, без секретов.

- [ ] Написать tests/contact.test.mjs: длины на границах 2/3/200/201 и 9/10/3000/3001, произвольный контакт мессенджера, неверное направление, honeypot, 429, отсутствующая конфигурация, отказ/тайм-аут deliver, успешный deliver. До реализации запустить npm test и подтвердить ожидаемый отказ.
- [ ] Реализовать lib/contact.mjs и маршрут сервера: ограничения размера тела, серверная валидация, ограничение частоты, тайм-аут доставки; не сохранять обращения в логи. Канал подключать только после получения реального получателя; до этого явно возвращать 503.
- [ ] Реализовать клиентские состояния из ТЗ: подписи, ошибки, фокус, sending, блокировка повтора, успех после 200, сохранение текста при сбое. Не повторять запрос автоматически после неоднозначного тайм-аута.
- [ ] Запустить npm test; ожидаются все PASS. Проверить в браузере некорректный ввод, мессенджер, двойной клик, отключение сети и 503. Реальную доставку проверить отдельной заявкой после подключения канала.

### Task 4: Кейсы, SEO, итоговая проверка и передача

**Interfaces:** карточки ведут на реальные /cases/<slug>.html; контакты и canonical используют только подтверждённые адреса. Публичные данные согласуются владельцем.

- [ ] Подготовить страницы кейсов по шаблону ТЗ только из доступных реальных материалов или маркированных демо. Не создавать пустые индексируемые страницы.
- [ ] Добавить title/description/lang, Open Graph, favicon; robots/sitemap и canonical настроить после выбора домена. До этого тестовое окружение закрыть от индексации.
- [ ] Подготовить .env.example и README: установка, запуск, контент, доставка, секреты, хостинг. Юридическую страницу заполнить только под реальную обработку; отсутствие данных записать как ограничение публикации.
- [ ] Проверить все размеры из Global Constraints, увеличенный текст, длинные заголовки, iOS/Android при наличии, актуальные браузеры, клавиатуру и контраст. Записать реальные условия и неподтверждённые платформы.
- [ ] Измерить вес ресурсов, LCP/CLS лабораторно; не выдавать лабораторные результаты за полевые INP. Исправить выявленные проблемы и повторить только затронутые проверки.
- [ ] Выполнить npm test, проверить ссылки/форму/демо, снять desktop/mobile скриншоты, провести финальный review относительно ТЗ; сохранить docs/verification.md.
- [ ] Передать работающий локальный результат и список недостающих материалов. Публиковать только после получения настроек и выполнения launch checklist из ТЗ; после публикации проверить HTTPS, индексацию и реальную доставку.

## Самопроверка плана

Все разделы ТЗ распределены: контент/дизайн → задача 1; интерактив/доступность → 2; форма/данные → 3; кейсы/SEO/проверка/передача → 4. Проект можно разработать локально до получения персональных материалов, но нельзя заявлять готовность production с фиктивными контактами или без доставки. Выбор доставки, реальные кейсы и юридические данные остаются входными материалами владельца, а не скрытыми предположениями реализации.
